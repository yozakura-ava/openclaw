# Fork delta — Catalog tmp-leak fix (bound captures to one successful generation)

Captured 2026-09-22. Re-applies the upstream fix theory from
[openclaw/openclaw#153038](https://github.com/openclaw/openclaw/pull/153038)
("bound catalog retries and plugin capture retention") and
[openclaw/openclaw#153041](https://github.com/openclaw/openclaw/pull/153041)
("reuse plugin captures during model catalog refresh") against the
yozakura-ava/openclaw 2026.9.5 fork.

## Symptom (sanitized)

`/tmp/openclaw-model-catalog-*` scratch directories accumulate on long-lived
gateways and are never reclaimed. Each contains dozens to hundreds of
`openclaw-plugin-build-*` capture subdirectories. Stale trees ranged from
7 GB to 58 GB; an aggregated cleanup on one host recovered roughly 250 GB.

Observed on OpenClaw **2026.9.5**. Verified via `lsof +D` and
`/proc/<pid>/fd` scans across all gateway worker processes — no live process
held the directories, confirming they were orphaned rather than in-use.

## Code path (v2026.9.5)

- `src/agents/prepared-model-catalog-worker.ts` — `prepareWorker` creates the
  scratch dir via `fs.mkdtempSync(path.join(tmpdir(), "openclaw-model-catalog-"))`
  and passes it as `sourceCaptureDirectory` to the catalog worker pool.
- `src/plugins/plugin-package-metadata-capture.ts` — `createPluginSourceCapture()`
  creates `openclaw-plugin-build-*` subdirs; `dispose()` / `disposeAsync()`
  remove the subdirs with `fs.rmSync(..., { recursive: true })`.
- `src/agents/prepared-model-catalog.worker.ts` (parentPort branch) — the
  worker-task handler used a `Set<PluginRegistry>` (`retainedRegistries`)
  pattern to deduplicate retained generations across tasks. Each new
  registry was added to the set; the captured scratch tree rooted at
  `sourceCaptureDirectory` survived across all of them.

The in-source comment said _"A compute worker's parent reclaims this scratch
directory after confirmed exit"_ — the comment described an invariant that
worker crashes (`SIGKILL`, `restartOnError`, pool teardown failure) bypassed.

## Root cause

The parentPort branch retained plugin generations keyed by their registry,
not by worker task. Each abnormal worker lifecycle (crash, kill -9, pool
teardown) leaked the scratch tree that contained every `openclaw-plugin-build-*`
created during that lifetime. Long-lived gateways accumulated one ~30–60 GB
leak per abnormal event.

A secondary contributor: `facts.templateModelRegistry.getAll()` was called
outside `withPluginRuntimeGenerationScope`, so lazy normalization could
attach provider hooks to a stale metadata snapshot, triggering additional
re-acquisitions.

## Fix theory (adapted from upstream)

The upstream PRs restructure the worker-task handler around a single
`current` slot. On every successful task the previous generation is
released and the new one takes its place, so at most one successful
generation is retained between tasks. Failed acquisitions never enter the
retained slot. The outer scratch directory is implicitly bounded by the
`withPluginSourceCaptureDirectory(data.sourceCaptureDirectory, ...)`
context lifetime.

The fix has two cooperating changes:

1. **Bounded retention in the parentPort handler.** Replace
   `preparedGeneration` + `retainedRegistries: Set<PluginRegistry>` with a
   single `current: { fingerprint, prepared, release } | undefined` slot.
   On a successful run, swap `current` to the new generation and release
   the previous one _after_ the swap holds (so a concurrent task never
   observes an empty slot). On a failed run, release the attempted
   generation without retaining it.

2. **Scoped lazy normalization.** Wrap
   `facts.templateModelRegistry.getAll()` in
   `withPluginRuntimeGenerationScope(pluginGenerationScope, ...)` so
   provider hooks attach to the selected catalog generation rather than a
   stale one.

## Why this is an adaptation, not a verbatim cherry-pick

The fork's lineage diverged from `upstream/main` by approximately 4,950
commits before the migration to 2026.9.5. The upstream PRs introduce two
new symbols (`retainPreparedPluginRegistry`, the `WorkerGeneration` type
shape with a `discovery` field) that this fork does not need:

- `loadAgentRuntimePluginRegistryHandle` in this fork returns a registry
  synchronously inside the request scope, so a separate discovery-release
  slot is unnecessary.
- `ownPreparedPluginGeneration(generation).retain()` already exists and
  returns a release function with the same semantics upstream's
  `retainPreparedPluginRegistry` provides.

The adapted change touches only `src/agents/prepared-model-catalog.worker.ts`.
A direct cherry-pick would have required conflict resolution in seven files
across two PRs plus introducing the two unused symbols.

## Files changed

- `src/agents/prepared-model-catalog.worker.ts`
  - Import swap: `retainPreparedPluginGeneration` → `ownPreparedPluginGeneration`
    (the new parentPort handler uses `.retain()` directly so it can hold or
    drop the reference depending on the run outcome).
  - Added `type WorkerGeneration = Awaited<ReturnType<typeof prepareWorkerGeneration>>`
    local alias for the single-slot shape.
  - Replaced `preparedGeneration` + `retainedRegistries` with a `current`
    slot. The handler now:
    - Reuses the previous generation if the fingerprint matches (no
      re-acquisition).
    - Otherwise attempts a new preparation, retains it only if the
      reconstructed fingerprint matches and the run commits, and releases
      the previous generation after the swap.
    - Discards attempted generations that never commit (mismatch, failure).
  - Wrapped `facts.templateModelRegistry.getAll()` in
    `withPluginRuntimeGenerationScope(pluginGenerationScope, ...)` so lazy
    normalization keeps provider hooks on the selected generation.

## Risk assessment

- **Blast radius:** worker-thread internal lifecycle only. The public
  `runPreparedModelCatalogWorkerRequest` signature is unchanged. No
  gateway-facing behavior changes.
- **Behavior change for failure paths:** failed acquisitions no longer
  pollute the retained set. Previously, the `retainedRegistries` Set
  could grow unbounded across plugin churn. Now a failed run is fully
  discarded and the scratch dir under `sourceCaptureDirectory` is no
  longer pinned by a leaked generation.
- **Behavior change for success paths:** when the fingerprint matches the
  previous successful run, the same `prepared` is reused without an
  additional acquisition, mirroring upstream's behavior.
- **Protected paths:** the change does not modify gateway config,
  schema, or any path outside `src/agents/prepared-model-catalog.worker.ts`.

## Local remediation until the PR lands

A periodic sweep of unowned (no live FD) `openclaw-model-catalog-*` dirs
older than 24 hours remains the safe interim measure for hosts running
v2026.9.5.
